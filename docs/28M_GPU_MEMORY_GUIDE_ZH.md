# 28M 模型的 GPU 显存与训练效率说明

本文记录 SaddleLLM 28M 中文模型在单张 16 GiB GPU 上训练时的显存计算、实测数据和调参原则。核心结论是：**显存是容量，不是利用率；判断 GPU 有没有真正跑起来，应优先看 GPU utilization 和 tokens/s。**

## 1. 当前模型和训练批次

当前模型参数量为：

```text
N = 28,319,616 parameters
```

第一阶段配置为：

```text
micro batch = 64
sequence length = 256
每步 token 位置数 = 64 × 256 = 16,384
precision = BF16
optimizer = AdamW
gradient checkpointing = false
loss chunk size = 512
```

## 2. 模型状态为什么不到 1 GiB

训练时不只保存模型权重，还要保存梯度和优化器状态。下面按较保守的混合精度 AdamW 估算，即使实现没有使用独立 FP32 master weights，也先把它算进去。

| 项目 | 每参数字节数 | 计算 | 约占显存 |
|---|---:|---:|---:|
| BF16 权重 | 2 | `N × 2` | 54.0 MiB |
| BF16 梯度 | 2 | `N × 2` | 54.0 MiB |
| FP32 master 权重（保守计入） | 4 | `N × 4` | 108.0 MiB |
| Adam 一阶矩 `m`（FP32） | 4 | `N × 4` | 108.0 MiB |
| Adam 二阶矩 `v`（FP32） | 4 | `N × 4` | 108.0 MiB |
| 合计 | 16 | `N × 16` | 约 432.1 MiB |

具体计算：

```text
28,319,616 × 16 bytes
= 453,113,856 bytes
= 432.1 MiB
```

不同 PyTorch/优化器实现可能不创建独立 FP32 master 权重，也可能为梯度或状态建立额外缓冲区。因此实际值会变化，但 28M 模型的永久模型状态通常仍明显低于 1 GiB。参数量已经包含词嵌入，并且当前输入嵌入和输出权重是共享的，不需要把词表矩阵重复计算两次。

## 3. 其余显存去了哪里

训练显存可以粗略拆成：

```text
总显存占用
= 模型权重
+ 梯度
+ 优化器状态
+ 前向激活
+ 输出 logits / 交叉熵临时张量
+ CUDA context、cuBLAS/cuDNN/SDPA 工作区
+ PyTorch caching allocator 保留区
+ 桌面显示和其他 GPU 进程
```

### 3.1 激活

激活随 batch、序列长度、层数和隐藏维度增长。当前单个 `[batch, sequence, hidden]` BF16 张量约为：

```text
64 × 256 × 384 × 2 bytes = 12 MiB
```

一个 Transformer 层会为注意力、Q/K/V、MLP、归一化、残差和反向传播保存多个张量；10 层叠加后会达到数 GiB。这里不能只拿上面的 12 MiB 乘 10，因为每层要保存的中间量不止一个。

### 3.2 32K 词表的输出层

如果一次生成完整 logits，当前每步理论大小是：

```text
64 × 256 × 32,768 × 2 bytes = 1 GiB
```

当前实现把线性输出和交叉熵按 512 个 token 分块，每个分块的原始 BF16 logits 约为：

```text
512 × 32,768 × 2 bytes = 32 MiB
```

这样避免同时保留约 1 GiB 的完整 logits，也降低反向传播峰值。分块太小会增加小算子调用，分块太大又会增加显存峰值，所以必须用 tokens/s 实测，不能只靠猜测。

### 3.3 基础占用

这台 RTX 4090 Laptop GPU 在训练前，Windows 桌面和已有 GPU 进程本身约占 3.1 GiB。`nvidia-smi` 显示的 6.7–6.9 GiB 是整张卡的总占用，不全是模型独占。

## 4. 为什么 6.7 GiB 也能把 GPU 跑满

GPU 有两个不同概念：

- 显存占用表示“存了多少数据”，类似仓库用了多少空间。
- GPU utilization 表示“计算单元有多少时间正在工作”，更接近机器是否忙碌。

小模型可以只占一部分显存，同时让矩阵乘法单元持续工作。当前正式训练的实测值为：

| 配置 | 显存 | GPU utilization | 吞吐 |
|---|---:|---:|---:|
| batch 64、单进程取数 | 约 6.9 GiB | 约 80% | 约 54.9K token/s |
| batch 64、4 个持久化取数 worker | 约 6.7–6.9 GiB | 约 97% | 约 72K–76K token/s |
| batch 128 压测 | 约 10.1 GiB | 100% | 约 65K–67K token/s |

batch 128 确实多占了约 3.2 GiB，但速度反而更低。原因包括更大的单步输出层工作量、分块交叉熵调用、显存带宽和功耗/频率限制。对固定 token 预算来说，大 batch 还会减少参数更新次数，并不必然改善最终质量。

因此当前正式训练选 batch 64：它不是显存占用最高的配置，而是已测试配置里实际 tokens/s 更高的配置。

## 5. 正确的效率判断顺序

训练时按下面顺序判断，不要把“显存是否塞满”放在第一位：

1. `train_tokens_per_second` 是否最高且稳定。
2. GPU utilization 是否长期接近 90%–100%。
3. loss 是否持续下降、grad norm 是否有限且稳定。
4. 是否没有 OOM，并给评估、保存和 CUDA 临时工作区留下峰值余量。
5. 相同 token 预算下，验证 loss/perplexity 和生成样例是否更好。

显存留有余量不等于浪费。刻意把显存塞满可能导致 OOM、内存碎片、保存/评估峰值失败，或者像 batch 128 压测一样让训练更慢。

## 6. 剩余显存应该怎样有价值地使用

优先级如下：

1. 在第二阶段把上下文从 256 提升到 512，真正训练更长依赖。
2. 对 512 长度重新压测 batch 16、32 等档位，仍以 tokens/s 和验证质量选型。
3. 28M 基线稳定后，再训练 60M–100M 模型；更大的模型会自然提高模型状态和激活显存。
4. 只有实测更快时才扩大 batch 或 loss chunk；不能只因显存空闲就扩大。
5. 继续优化数据加载、融合算子和编译路径，目标是减少 GPU 等待时间。

## 7. 本轮实测结论

2026-09-23，本机单卡 RTX 4090 Laptop 16 GiB：

```text
模型参数：28,319,616
batch：64
sequence length：256
每步 token：16,384
显存：约 6.7–6.9 GiB / 16.0 GiB
GPU utilization：约 97%
稳定吞吐：约 72K–76K token/s
```

这个结果说明当前第一阶段已经从“数据加载受限”优化为“GPU 计算基本跑满”。下一轮优化应以验证质量、长上下文和算子吞吐为目标，而不是单纯追求更高显存占用。
