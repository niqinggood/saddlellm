# 远程 L20：Qwen3-4B 原生流式合批验证

日期：2026-09-29。本次验证把同一份候选 wheel 放到用户指定服务器的独立目录，
对照 **Saddle 原生服务合批 OFF / ON**。不是与 HF、Ollama、vLLM 的横向排名，也不是训练或答题质量评测。

## 环境与保护范围

- Linux / NVIDIA L20，`nvidia-smi` 总显存 49,140 MiB；既有服务约占 35,632 MiB。
- Python 3.10.12、Torch 2.6.0+cu124、Transformers 4.57.6、FastAPI 0.141.1、Uvicorn 0.53.0。
- 本地已有 `/home/medmodel/models/Qwen3-4B`，非量化 Qwen3 稠密模型，CUDA BF16。
- 新建独立测试环境，安装候选 wheel；只读复用原环境的 Torch 等依赖，不覆盖既有服务包、不升级全局环境。
- 不关闭医疗 Web、聊天、向量检索或重排服务。测试仍会共享 GPU 算力，不能称为隔离负载。
- 当时可用显存约 13.2 GB，不足以再安全加载 Qwen3-8B BF16，因此本次不借暂停业务来测试 8B。

候选 wheel 的 SHA256 为 `272af3a9adc8d960780e4175c224c17e7bd4afb08b62731317c5a8ba07f0df64`。
报告的 `imported_package` 指向新建环境，运行时源码哈希取自实际导入的安装包，而不是旁边的源码副本。

## 测试协议

使用 `tools/benchmark_native_stream_batching.py`：每个进程只加载一份权重，两个临时 loopback 服务共享模型，
分别关闭/开启 `native_stream_batching`。逐目标预热两轮，再随机顺序配对测量七轮。

- 真实 HTTP `/v1/completions` 的 SSE；输入先经 Qwen 聊天模板处理，因此是聊天格式输入，不是随机 token。
- 两边都使用 `enable_thinking=False` 的输入模板、`temperature=0`、48 个生成 token 上限。
  **加速比不是靠一边关闭思考而另一边保留思考取得的。** 这也不代表默认思考模式的网页聊天速度。
- 单 CPU 计算线程、无跨请求前缀缓存、`batch_wait_ms=5`；GPU 上既有服务未停止。
- 等长 C4：四个请求使用相同问题，模板化后 25 个输入 token。
- C1：相同输入，单客户端；不会有跨请求合批。
- 混合 C4：中英四个不同问题，输入长度为 25、23、36、36；其中两条恰好同长度，不等于四条都不同长度。
- EOS 未关闭。48 token 是请求预算，部分回答可能因预算被截断；这里不把回答完整性当作已通过的质量评测。

吞吐是**所有并发请求合计的输出 token/s**。首包为第一个非空可见文本，包含 tokenizer 缓冲和网络调度。

## 结果

下表前四项 OFF/ON 的服务许可上限保持相同（C4 为 4；C1 测试为 2，但只有一个客户端请求）。
它们不是“默认串行服务”的对照；默认串行许可的保守对照另列。

| 负载 | OFF → ON 总输出 token/s | 配对耗时比中位数 | P95 可见首包 OFF → ON | 完整性能门槛 |
| --- | --- | --- | --- | --- |
| 同提示 C4，第一轮 | 36.43 → 69.70 | 1.912× | 240.30 → 156.50 ms | 通过 |
| 同提示 C4，独立复测 | 36.24 → 69.91 | 1.922× | 279.14 → 154.77 ms | 通过 |
| 单请求 C1 | 50.89 → 48.85 | 0.974× | 46.12 → 120.49 ms | 未通过 |
| 混合提示 C4 | 36.26 → 53.56 | 1.547× | 348.69 → 251.53 ms | 通过 |
| 同提示四客户端：原生默认串行许可 → 合批四许可 | 50.54 → 70.13 | 1.387× | 2897.83 → 154.10 ms | 通过 |

最后一行是更保守的对照：基线服务 `max_concurrency=1`、候选为 4，但两边都有四个并发客户端。
它只改变原生请求许可策略，不代表所有 `serve` 默认后端和参数；模型、精度、输入模板、生成预算保持一致。
**相对这个串行许可基线，总吞吐约提升 39%，不能宣传成默认原生服务普遍翻倍。**
相对配置为四许可、分别步进的原生基线，两轮约 1.9 倍；两种结论的基线不同，必须分别说明。
串行基线的 P95 首包含排队等待，不能把约 2.9 s → 154 ms 全部解释成模型单步计算变快。

两轮同提示 C4 均七对全胜，每个目标有 28 个计时请求；C1 每个目标有七个请求。
上述所有输出文本、实际 token 数一致，结束后接入/请求/KV 组引用归零。C1 没有发生批量前向，
单请求直通没有在这次服务器测试中带来提速，首包还有明显回退，因此继续默认关闭。

混合测试实际最大 batch=2、含预热有 188 次批量前向；只是其中同长度的两条请求可以部分合批，
不是实现了任意长度 padded/ragged attention。配对耗时比中位数与总 token/s 的比值是两种统计量，不能混用。

## 正确性与性能门槛

检查输出文本散列、实际 token 数、结束后的接入/请求/KV 引用、是否真正执行了批量前向。
速度验收还要求至少七对、配对中位提升不少于 3%、至少 85% 配对更快、P95 可见首包回退不超过 5%、
峰值 PyTorch allocated 显存增幅不超过 5%。allocated 不是驱动显示的整卡占用。

即使平均总吞吐提高，只要文本不一致、实际未合批或首包超出门槛，都不宣布完整验收通过。
这些小规模确定性测试仍不代表广泛任务质量、长上下文或长期生产稳定性。

## 发现的下一步优化点

第一轮 C4 的实际最大 batch 是 3，而不是 4；这里 C4 指四个并发用户，不代表每次四条都合在一起计算。
含预热的健康计数器记录 423 次批量前向、423 次 KV 组创建和 8,981,839,872 字节历史复制。
因此本轮即使取得加速，KV 复用仍不理想。

从当前实现看，执行器每次 `step()` 重建活跃 cohort 集合；在 B3 解码与另一请求的 B1 步进交替时，
未参与当前调用的 B3 组会被丢弃，随后再次合组。后续应验证“保留未被本次步进修改、但仍有活跃请求的组”，
并继续保证成员退出、共享存储、显存上限和取消清理正确。本次验证没有在服务器上临时改写推理实现来美化结果。
