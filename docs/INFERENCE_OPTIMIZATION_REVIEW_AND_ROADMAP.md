# SaddleLLM 推理优化复盘与后续路线

材料日期：2026-09-29。面向项目介绍、技术交流与后续开发决策。
这是对已有源码和保存实验的整理，**不是本次又部署了一套新服务或重跑了全部性能实验**。
讨论的是推理执行效率、服务能力和正确性，不是重新训练模型使它更聪明。

后续进展：[BF16 合批分叉与临时显存修复](NATIVE_BF16_BATCH_FIX_20260929.md) 已解决所测 28M 案例，
新增受限 CUDA BF16 逐行 Linear 兼容路径。之后已实现 [显式原生 SSE 合批](NATIVE_STREAM_BATCHING_20260929.md)，
包含单请求直通、稳定行排序、有限步数对齐及真实 HTTP 验证。下文保留初版问题与路线背景；
混合长度实质合批、分页 KV、长 prefill 隔离和历史 8B 固定微批质量问题仍未完成。

## 一、一分钟讲清楚：我们靠什么达到目前的水平

Saddle 的推理改进不是单一开关，而是逐层减少重复工作：

1. **执行层自己掌握**：兼容模型的前向、缓存、采样、停止和流式生成进入 Saddle 原生实现，不仅是包装外部 `generate()`。
2. **少搬历史数据**：KV 几何扩容、预留 token/mask 缓冲；适配窗口层的环形 KV；可选前缀快照。
3. **少做重复计算**：prefill 只投影最后位置 logits、合并适合的 QKV/gate-up 投影、受限 GQA 解码不重复展开 KV。
4. **让多个请求一起算**：先有非流式固定微批，再新增实验性逐步合批解码执行器，复用合组后的 KV。
5. **大模型显式轻量化**：Qwen3 W8A16 权重压缩，加上小行数解码和较大输入的两套 Triton 计算路径。
6. **避免无效工作与失控排队**：输入预算、有限接入、队列背压、断连取消、异常清理和真实 token 统计。
7. **不只看速度**：同权重对照、输出核验、反向顺序复测、失败记录、真实 SDK 和独立安装包验收。

这些改动发生在不同阶段、适用于不同路线，**不能把各实验的加速倍数相乘，也不能说所有能力默认同时开启**。

## 二、过去的问题，具体改了什么

“过去的问题”包括已经修复的缺陷、原有设计限制和实验中新发现的问题；不把全部旧实现都描述为错误。

| 层次 | 原有问题或限制 | 做过的改动 | 当前范围与代价 |
| --- | --- | --- | --- |
| 原生执行 | 仅有通用模型调用，不足以控制模型内部的解码和缓存路径 | `SaddleForCausalLM`、`NativeGenerationSession`，统一 prefill/step/生成逻辑；增加 Qwen3、Qwen2、Llama 受限稠密适配 | 明确选择原生路线；完整版 DeepSeek/Kimi/MiniMax 不能由蒸馏版适配推导为已支持 |
| KV 历史 | 逐步拼接会反复分配、复制已有 KV | 请求独立的几何增长缓存，容量够时只追加新 token | 原生生成已有能力；不是分页缓存，扩容仍有复制和瞬时内存开销 |
| token/mask | 每步拼接序列与 mask；无 padding 时重复处理全一 mask | 预留本次预算内的缓冲，追加写入；合格路径省去冗余 mask 处理 | 不修改输入，不把空余缓冲暴露给 attention；不是无限上下文 |
| prefill 输出层 | 生成下一 token 时不需要所有 prompt 位置的完整词表分数 | 生成路径使用最后位置 logits | Transformer 仍处理完整 prompt；训练 forward 保留完整监督，不等于分块 prefill |
| 线性投影 | Q/K/V、gate/up 分别调用，启动和调度次数多 | 在安全条件下合并投影；跳过恒等残差乘法 | 旧逻辑权重可复用，不重训；有 bias、adapter、hooks、低秩等情况必须按资格跳过，低精度仍需核验 |
| GQA 解码 | 部分回退路径把 K/V 重复展开到查询头数 | 合格的 CUDA 单 token 路径折叠查询头，读取紧凑 KV；有原生 Flash GQA 能力时优先使用 | 只适用受限形状和内置处理器；兼容性优先路线可能不用它，不是自研 FlashAttention |
| 窗口注意力 | 模型只需窗口，但历史 KV 不应无限驻留 | 按模型原有窗口配置使用镜像环形缓存，保留绝对位置 | 每窗口层最多 W 个逻辑 key、2W 个物理槽位；全局层不裁剪，不改变已训练模型注意力范围 |
| 重复 prompt | 相同提示重复做 prefill | 可选有容量/LRU/失效检查的前缀快照，命中后恢复私有 KV | 默认关闭；copy-on-hit，不是答案缓存、零拷贝共享或通用 radix tree；短 prompt 未必获益 |
| 固定微批 | 单请求调用不能自动利用请求间的批量矩阵计算 | 非流式 greedy 请求按兼容条件合批；可选长度桶、padded token 预算及队列 token 上限 | 显式 `--batch-size`；开始后不能插入新请求，提前结束行仍可能占用该批计算 |
| 逐步执行 | 多个独立 session 轮流 step，仍是多次 B1 模型前向 | 新增 `NativeBatchDecodeRunner`：等上下文分组、一次 B×1 前向、持久合组 KV、每行独立结束 | 实验性 import API，仅合批已验证的 FP32 稠密 greedy 路径；尚未接入默认 HTTP 服务 |
| 8B 驻留与带宽 | 浮点权重驻留大，小批解码容易受权重读取影响 | 显式 W8A16；INT8 隐藏层权重、浮点激活、FP32 scale；Triton GEMV/GEMM 按输入行数分派 | 实验性 Qwen3 稠密 CUDA 路线，需要兼容 Triton；量化有质量代价，不是无损 BF16 加速 |
| 断连与清理 | 非流式客户端离开后仍可能排队/生成；取消协程不等于停止模型线程 | 断连监听、排队撤销、逐步协作停止；实际模型退出后才释放许可；监听任务清理 | 修复已进入相应源码路径；不能强杀 kernel；既有运行进程不会自动加载新代码 |
| 服务交付 | 启动、接口和内部执行状态不易一致核验 | CLI/import 统一入口、文本 OpenAI 接口、SSE/真实 usage、输入与上下文校验、健康状态、环境诊断和 wheel 验收 | 兼容文本 API 子集，不是全量 OpenAI API；公网仍需网关、TLS 和适当鉴权 |

代码入口与详细使用说明见文末索引。

## 三、最容易混淆的三种“并发/合批”

| 方式 | 每轮怎样计算 | 能否在中间换请求 | 当前地位 |
| --- | --- | --- | --- |
| 多个独立 session / 请求并发 | 每个请求分别调用模型；多个线程不等于一次 GPU 合批 | 可单独管理请求，但未自动合成一次前向 | 本轮新执行器的对照基线 |
| 原有固定微批 | 一批请求共同调用批量生成 | 批开始后不插入新请求 | 已有原生非流式服务可选能力 |
| 新逐步合批执行器 | 兼容的 live session 每步共享一次前向 | 调用方可在步边界移除/加入请求，只有兼容组才合并 | 实验性执行层，还没有完整服务调度器 |

**框架不是直到这次才有批量计算。** 本轮 139 → 519 token/s 对照的是“四个独立 session”与“新逐步合批执行器”，
不是新执行器与原有固定微批的优劣对照，不能据此声称固定微批又提速约四倍。

### 本轮的代码流程

```text
每个请求独立 prefill，得到各自 KV 与首 token
  → runner.step(live_sessions)
  → 校验模型、精度、缓存、参数与上下文长度
  → 不兼容：原有单请求 step
  → 兼容：首次复制历史到合组 KV，此后复用
  → 一次 model.forward([B, 1])
  → 各行 logits 回到各自 session，分别采样/判断 EOS/stop/输出
  → 下一步更新成员；异常整组失效，禁止从半更新 KV 恢复
```

四个请求、每个固定生成 48 token 时：

- 独立执行：`4 × 48 = 192` 次 forward。
- 新执行器：`4` 次单独 prefill 产生首 token，随后 `47` 次批量 decode，共 `51` 次 forward。
- 总输出仍为 `4 × 48 = 192` token；没有少生成、换权重或关闭思考来制造差值。

原先已经有增量 KV，本轮新增的是**合批以后也能持续复用合组缓存**，不是把“首次拥有 KV cache”当作成果。
减少模型调用可降低重复的主机调度和算子启动开销，让批量矩阵计算更充分利用硬件；
权重读取、kernel 启动等各占多少收益，尚未用 profiler 分别量化，不能把机制推断写成精确归因。

## 四、目前的水平：把不同实验分开看

### 4.1 最新 28M FP32：新合批执行层

本地 Windows，RTX 4090 Laptop；CPU 对照使用一个 Torch 线程。
同一检查点、四个不同且等长的 32-token 合成输入、每请求固定输出 48 token，greedy、关闭 EOS/前缀缓存。
计时包含 session 创建、prefill、decode、采样、合组复制、结果复制和清理，不包含加载/预热、分词和 HTTP。

| 环境 | 逐请求中位耗时 → 合批 | 聚合输出 token/s | 配对耗时比中位数 |
| --- | --- | --- | --- |
| CPU FP32 | 1.4025 → 0.6590 秒 | 136.9 → 291.4 | 2.12× |
| GPU FP32 | 1.3827 → 0.3700 秒 | 138.9 → 519.0 | 3.56× |

每轮预热后 7 对 AB/BA，最终两组均 7/7 更快且 token ID 一致；之前的独立轮次也保留。
吞吐分别取两条路线中位数，配对比则先逐对计算，因此不能拿表中吞吐比替代配对统计。
GPU 峰值 PyTorch allocated 约增加 2.4%，不是整卡显存；CPU 内存未测。

**519 是四个请求的总吞吐，不是单用户速度，不是 8B，也不是 HTTP 服务成绩。**
小模型可能更受启动/调度开销影响，结果不能外推到大模型。CPU 单请求负对照没有稳定收益。
详见 [实现与全部实测](NATIVE_BATCH_DECODE_20260929.md)、
[最终 CPU 原始记录](../artifacts/native_batch_decode_20260929/cpu_b4_final.json)、
[最终 GPU 原始记录](../artifacts/native_batch_decode_20260929/cuda_b4_final.json)。

### 4.2 历史完整 Qwen3-8B：量化、投影合并与固定微批

以下是另一个阶段、另一台 Linux L20 的历史实验，不与上面的 28M 相加或比较排名。

- 同一套 W8A16 算子、单请求模型调用：Saddle 未合并投影 **29.45 → 合并后 34.84 输出 token/s**，约 +18.3%。
  参数与 buffer 驻留约 9.44 GB，较原始 BF16 权重约减少 42%；不代表整进程显存同比下降。
  293 个预测位置的自编文本质量抽查困惑度约上升 0.82%，不能称量化无损或业务质量已保证。
  [完整条件和证据](NATIVE_INT8_8B.md)。
- 同一 W8A16 路线的非流式 HTTP C8：逐请求 **32.43 → 固定微批 252.78 输出 token/s**。
  这是短重复提示、greedy、每请求 64-token 预算的有限实验；**微批与串行文本哈希不同，原因和业务质量尚未验收**。
  因此只是有条件的吞吐观察，不能宣传“无损 7.79 倍”，不能证明单用户 252.8 token/s。
  [服务条件和原始记录](SIMPLE_SERVING_VALIDATION_20260927.md)。

这两项和最新 BF16 合批分叉是不同实验；没有证据说明它们已经定位到同一个原因。
也没有完成同条件的完整 8B vLLM/Ollama 优劣排名。

### 4.3 资源管理：用户离开后不继续浪费计算

最近的 28M CPU 真实 TCP 断连实验中，废弃长请求由每次执行 64 步减少到 1 步；
之后短请求中位响应，两轮分别为 **480.3 → 34.3 ms**、**1258.4 → 85.5 ms**。
这改善的是“废弃工作阻塞后来请求”，不是普通请求吞吐提高十几倍；绝对时延也存在机器负载波动。
[断连实现与报告](INFERENCE_LIFECYCLE_20260929.md)。

窗口缓存、投影合并等早期实验见 [窗口 KV](INFERENCE_WINDOW_AND_SCHEDULING.md) 和
[历史性能对照](INFERENCE_PERFORMANCE_COMPARISON.md)。不要挑出每轮最高值拼成一条累计加速曲线。

## 五、修复与失败同样是工程成果

### 已修复的数值兼容问题，不等于全部低精度问题都修好了

真实 DeepSeek-R1-Distill-Qwen-1.5B 曾在原生 SDPA 与 HF BF16 对照中分叉。
为相应适配环境增加 `sdpa_reference` 后，同前缀 32 步 logits 差为 0，四条提示的 HTTP SSE 文本和 usage 一致。
这是特定模型/环境的兼容性修复，可能更慢，详见 [服务迭代](NATIVE_SERVING_ITERATION_20260928.md)。

本轮新执行器的 28M BF16 合批仍失败；换成 `sdpa_reference` 也没解决。
强制两条路线使用同一历史 token 后，第 25 个生成 token 首次 argmax 不同，192 个请求步有 3 处差异。
说明不只是“先前输出不同导致后面不同”，但还没有定位到具体算子，也没有完成任务质量归因。
**当前只放行该执行器的 FP32 合批，BF16/FP16 继续逐请求执行。**

### 没有默认启用的路线

| 尝试 | 为什么没有算作已交付提速 |
| --- | --- |
| 逐 token 线程轮转、独立有界线程池 | 个别首字指标改善，但吞吐/尾延迟或复测稳定性不合格 |
| 控制张量/EOS 微优化 | 局部微基准明显更快，完整模型约 1.7%/2.5%，未达预定 3% 门槛 |
| 单请求状态复用、Q/K RoPE 合并 | 没有取得稳定的整模型收益，保持关闭或实验性 |
| 前缀部分复用 | 已有显式实验入口，但短提示上的复制/查找可能得不偿失，不默认打开 |
| BF16 新合批 | 输出一致性失败，不能只看吞吐放行 |
| 历史 W8A8、CPU BF16 预排布、编译候选 | 质量、数值或速度验收未过，不能包装为当前公开默认能力 |

保留这些记录的目的，是避免下一轮重复踩坑，也避免把“写了代码”误当成“优化已经成功”。

## 六、后续怎么优化：按风险和收益排序

以下全部是**待做路线，不是已实现功能，也不是预计倍数或交付日期承诺**。
原则：用户继续使用简单的 `serve` / import；复杂的兼容性判断、调度和回退放在框架内部，并可观察实际选择。

| 优先级 | 工作 | 具体做法 | 做完如何判断 |
| --- | --- | --- | --- |
| P0 | 把低精度正确性问题定位清楚 | 固定权重/环境，teacher-forced 对比 B1/B2/B4/B8；逐层检查投影、RoPE、KV 位置、attention、norm 和 lm_head，找到首次偏差；把 28M 新合批与 8B 旧固定微批分开调查 | 先形成最小复现；控制流程改动保持 token/结束/usage 一致。若数值内核不可位级一致，单列误差和任务质量标准，经明确验收后才开放，不能偷偷放宽现有门槛 |
| P1 | 接入原生流式服务的实际批量执行 | 在已验证路径上连接 session 队列与新 runner，统一管理请求加入、退出、慢客户端、异常和关闭；让 SSE token 交付与模型执行解耦 | 真实 OpenAI SDK/TCP 通过；看到实际 B×1 forward；吞吐、可见 TTFT、TPOT、P95 同测；先内部/显式试验，不直接替换默认 |
| P2 | 提高混合长度下的合批率 | 先用上下文长度分组评估真实收益，再设计可变长度 attention 与正确 mask/position；不能把长度桶直接叫 ragged batching | 不同 prompt 长度、不同输出预算、padding/stop/采样均无串扰；报告合批率、回退率和 padding 浪费，不只跑等长峰值 |
| P3 | 减少 KV 分配、重组复制和闲置空间 | 先做有字节预算和所有权的 KV 缓冲池/容量桶，明确回收时机；只有数据证明需要时再升级块管理、引用计数和分页 attention | 跟踪 KV 实际字节、历史复制字节、分配次数、取消后驻留；同质量同负载下峰值显存或持续吞吐有收益，无跨请求数据串扰 |
| P4 | 长 prompt 与 decode 协同调度 | 逐块 prefill，按 token 预算插入已有 decode；保留绝对位置、完整 prompt 因果关系和停止/取消语义 | 长短混合负载下首字与 P95 改善，prefill 输出与完整路径一致；短请求优先不能使长请求饥饿 |
| P5 | 依据 profile 做更深算子和执行优化 | 先量化 CPU 调度、kernel 启动、GEMM、attention、KV 复制与同步开销；对稳定形状评估 CUDA Graph；只对真实热点考虑 Triton 融合或 C++/CUDA 扩展 | 与同条件未优化实现逐项 A/B；计算图地址、容量增长、mask、RNG、取消不兼容时安全回退；未测到收益就不增添默认复杂度 |
| 发布前并行项 | 把成果变成可用交付 | 核对 CLI/import/依赖/平台矩阵，修复已有导出冲突等 lint 问题；干净环境 wheel 与真实服务验收；更新支持边界 | 不能用源码测试代替安装包测试；不能把登记了 CI 写成各平台已实测；现有服务升级需要独立部署步骤 |

### 最近一轮优先做什么

先完成 P0，再为 P1 建立最小内部服务原型。可并行设计监控与验证工具，但在正确性过关前不把 BF16 合批接成默认。
若 profile 提前确认主机启动开销主导，可以小范围验证 CUDA Graph，不必为了路线表顺序先重写完整分页引擎。
同样，如果主要瓶颈是长 prompt，优先分块 prefill；如果是显存驻留，则优先 KV 管理。

**现在不需要先写一整套 C++ 推理引擎。** 已有 PyTorch 原生执行和部分 Triton 算子可以继续承载优化。
C++/CUDA 是发现特定瓶颈后的实现选项，不是“变专业”或“必定更快”的前提。

## 七、下一轮验证方案

沿用 [统一验证方案](INFERENCE_VALIDATION_PLAN.md)，为新执行器增加以下重点：

1. 模型：本地可承载的 28M、Qwen3-0.6B、DeepSeek 蒸馏 1.5B；显存充足且负载隔离的环境再测完整 8B。
   不为实验擅停业务服务，不用小模型结果替代 8B。
2. 基线至少区分：独立 session、已有固定微批、新逐步合批；相同精度、模板、权重、输出策略和前缀命中状态。
   外部引擎另列，不能把换量化精度、关闭思考、缩短答案算成执行器提升。
3. 并发 1/2/4/8，输入 128/1024/4096、输出 32/128/512，但只选择模型与资源允许的组合。
   加入真实中文、英文、代码、数学提示，以及长短混合、自然 EOS 和不同 stop。
4. 模型层测实际生成 ID、prefill/decode 耗时、forward 形状、合批率/回退原因、KV 复制/分配和显存。
   服务层测实际 usage、聚合吞吐、首个非空文本 TTFT、每 token 延迟、P95/P99、排队与错误率。
5. 开发初筛至少 7 对 AB/BA、独立复测，配对中位数至少快 3%、至少 6/7 对更快。
   检查首字、尾延迟和显存的回归；这不是统计显著性或 SLA 证明，正式结论需要更多样本。
6. 单独做至少 30 分钟混合负载与断连/慢客户端/超载/故障测试，确认请求计数归零、资源回到稳定水平。
   CPU 内存、GPU allocated/reserved、驱动显存要分别命名；没有测到的指标明确写未测。
7. 保存代码/模型来源、原始输出与每次耗时；成功失败都留档。所有部署命令先在独立候选包和临时端口验收。

当前最近一次相关回归是 **675 项通过**，独立安装包相关测试 **75 项通过**，另有真实 SDK 冒烟通过；
不是整个仓库/全部平台验收完成。全仓 lint 仍有 `RolloutSample` 重复导出问题，本轮材料整理不修改运行时代码。

## 八、可直接用于项目介绍的一段话

> 我们把 Saddle 的推理能力分为原生执行、缓存、计算、调度和服务交付几层来改进。先减少 KV 和序列的重复复制，
> 再减少不必要的词表投影和线性调用，并为兼容大模型提供显式 W8A16 路线。并发方面，已有非流式固定微批，
> 最近进一步做了可逐步推进的合批解码执行器。28M FP32 四请求实测中，GPU 聚合输出吞吐约从 139 提升到 519 token/s，
> 同条件输出一致。但它还不是 8B 或默认 HTTP 服务成绩；BF16 新合批存在输出分叉，因此没有默认开放。
> 后续优先解决低精度正确性，再推进真实流式合批、混合长度和 KV 内存管理。我们保留失败记录，不用峰值数字替代质量和部署验收。

不要对外表述为“所有模型提升数倍”“单用户默认 519 token/s”“已经全面超过 vLLM”或“支持全部国产开源大模型”。
已接入成熟外部后端不等于它的全部能力由 Saddle 原生实现；支持架构适配也不等于所有品牌/变体已实测。
