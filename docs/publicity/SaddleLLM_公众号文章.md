# SaddleLLM 一条命令部署大模型服务

模型微调完成了，接下来怎样让应用真正用上它？

对一个做大模型应用的团队来说，模型能生成回答只是起点。还需要稳定的服务入口、统一的调用协议，以及对显存、并发、输入长度和失败请求的处理。我们在 SaddleLLM 2.40 中，把这些工作集中到了一个使用入口：

```bash
saddlellm serve /models/Qwen3-8B --model-name qwen3-8b
```

完成环境安装并准备好模型后，这条命令会启动文本推理服务，提供 OpenAI 兼容的对话与补全接口。在具备兼容 vLLM 的 Linux CUDA 环境中，默认入口选择 vLLM；其他环境明确选择本地路线并提示能力差异。显式选择原生 INT8 时，则进入 Saddle 自有推理路线。

SaddleLLM 面向的是需要训练、调整并部署自己模型的开发者。我们希望使用者少写一些重复的服务代码，同时能知道模型到底运行在什么后端上。

## 从训练结果到可调用的接口

SaddleLLM 已提供预训练、SFT、DPO、KTO 等训练入口，并围绕模型加载、评估与部署组织工作流。服务可以从命令行启动，也可以从 Python 启动：

```python
from saddlellm import serve

if __name__ == "__main__":
    serve("/models/Qwen3-8B", model_name="qwen3-8b")
```

应用侧可以继续使用 OpenAI 文本客户端，把服务地址指向自己的部署实例。当前接口覆盖模型列表、文本对话、文本补全、SSE 流式输出和实际 token 用量统计；工具调用、多模态和 Responses 等接口尚不在支持范围内。

这种统一入口的价值，主要体现在需要反复训练和部署的团队：原生模型、完整 HF 检查点和适配器都有相应的加载路线，但仍需满足各自的模型与环境要求。使用者不必为了每次试验重新实现 HTTP 服务。随附产品手册提供了具体的配置与调用步骤。

## 自有推理路线做了哪些优化

在完整 Qwen3-8B 上，我们已经实现了 Saddle 原生模型前向与逐 token 生成，并提供显式启用的 W8A16 路线。W8A16 表示部分权重使用 INT8 存储，激活保持 BF16 或 FP16；它是有损量化，不是“模型效果不变”的承诺。

这一实现也包含实际的 GPU 计算优化。Qwen3-8B 的 QKV 投影和 gate/up 投影可以合并，减少线性层的启动次数；小批解码使用专用的 Triton GEMV，较大的输入使用分块 GEMM。计算时读取压缩权重，不先展开一份完整的浮点权重矩阵。原生生成循环还会复用请求内的 KV 和解码缓冲。

这条完整 8B 路线实测的驻留参数及 buffer 约为 9.44 GB，相比原始 BF16 参数约 16.38 GB，减少约 42%。这个数字只描述参数及 buffer，不代表整个进程或峰值显存。项目中的原生 INT8 指南保留了实现细节与复现实验。

## 八请求微批的实测吞吐

我们在 NVIDIA L20 上，对完整 Qwen3-8B 的自有 W8A16 服务做了真实 HTTP 测试。

测试使用非流式原始文本补全，客户端并发为 8，同一个短提示输入 10 个 token，每个请求实际输出 64 个 token，贪心解码，关闭前缀缓存。每个设置预热 1 轮、计时 2 轮，共记录 16 个计时请求。

| 同一原生 W8A16 路线 | 总输出吞吐 | P95 响应时间 |
| --- | ---: | ---: |
| 逐请求执行 | 32.43 token/s | 15.754 秒 |
| 固定八请求微批 | 252.78 token/s | 2.039 秒 |

在这个有限测试中，聚合吞吐约为原来的 7.79 倍。直观地说，八个请求合计生成 512 个 token，大约用了两秒。

**这不是单个用户每秒得到 252.8 个 token，也不是默认配置或所有任务的速度。** 微批需要显式开启，目前主要面向原生非流式贪心请求。更重要的是，微批与串行路径的返回文本哈希不同，差异原因与业务质量仍待进一步验证。因此，这是一项有明确条件的性能观察，不能宣传成“无损提速”，也不能直接拿来证明超过 vLLM 或 Ollama。随附手册列出了实验条件，项目中保留了 HTTP 验收报告与原始记录。

## 高并发服务可以使用 vLLM

面向兼容的 Linux NVIDIA GPU 环境，SaddleLLM 也提供 vLLM 服务后端。Saddle 负责服务入口、请求校验、接入预算、取消与生命周期，vLLM 负责连续批处理和底层执行。分页 KV、CUDA Graph 等 vLLM 内部能力应归于 vLLM，而不是宣传为 Saddle 自研。相关能力见 [vLLM 官方文档](https://docs.vllm.ai/en/latest/)。

如果业务明确需要连续批处理，可以这样启动：

```bash
saddlellm serve /models/Qwen3-8B --model-name qwen3-8b --require-high-throughput
```

该选项会在无法选择兼容的 vLLM 路线时报告错误，避免使用者误以为自己已经获得连续批处理。它约束的是执行路线，并不保证固定吞吐。

原生 W8A16 微批和 vLLM 后端是两条不同的路线。前者让我们直接优化特定模型的执行与内存使用；后者让用户在统一的 Saddle 服务入口下使用成熟的高并发引擎。

## 与其他工具相比 应该怎样选

vLLM 本身已有简洁的服务命令。SGLang 提供服务启动和兼容的文本 API，并侧重 RadixAttention、前缀复用等能力。Ollama 提供 Windows、macOS、Linux 的便捷本地体验，也支持 OpenAI 兼容接口。这些能力都不是 Saddle 独有。[vLLM 快速上手](https://docs.vllm.ai/en/latest/getting_started/quickstart/)、[SGLang 官方介绍](https://docs.sglang.io/)、[Ollama 快速上手](https://docs.ollama.com/quickstart)、[Ollama 接口说明](https://docs.ollama.com/api/openai-compatibility)。

如果只是想在个人电脑上运行现成模型，Ollama 值得优先考虑。如果已经确定使用专业推理引擎，直接部署 vLLM 或 SGLang 也很方便。

SaddleLLM 的主要优势，出现在需要把模型训练、偏好优化和服务部署连接起来的场景。统一的命令行与 Python 入口，配合明确的后端选择和运行状态，可以减少团队在多个环节之间维护的胶水代码；同时，自有原生执行路线为特定模型的量化与计算优化提供了可继续改进的基础。

## 如何开始使用

以下命令适用于已经获取 SaddleLLM 2.40 源码、创建并激活独立 Python 环境的使用者。在源码目录安装本地服务依赖：

```bash
python -m pip install ".[serve]"
saddlellm serve /models/Qwen3-8B --model-name qwen3-8b
```

Linux CUDA 的 vLLM 部署应使用另一个独立环境，并安装 `.[serve-vllm]`，不要与本地服务的 Transformers 4 依赖混装。2.40 的本轮构建尚未上传 PyPI，请使用对应源码或 wheel，而不是假定包仓库旧版已有这些能力。

服务默认只监听本机。启动后先检查 `/readyz`，再通过 `/health` 查看实际后端。正式对外提供服务时，还需要鉴权、TLS、限流和业务质量验收。

我们欢迎开发者用自己的模型与真实业务题集试用 SaddleLLM。后续工作将重点放在原生微批的输出差异定位、混合负载测试，以及新版 vLLM 路线的完整 8B 验收。更好用的入口和可核验的性能结果，是我们持续改进的方向。
