# SaddleLLM 通用大模型平台边界

## 1. 产品定位

SaddleLLM 的目标是提供与行业无关的大模型全生命周期方案。医疗、护理、教育、政务或企业知识库是使用 SaddleLLM 的领域项目，不是 SaddleLLM 内部的硬编码分支。

产品主线以大模型为主：逐步成为能训练自有高水平模型的研发底座，而不是扩成通用
Spark/Flink/ETL 平台。CLI/import 保持简单，数据可靠性、训练稳定性、模型能力和部署效果
在底层分别验收。对标头部模型的路线和当前不足见
[头部模型研发路线](FRONTIER_MODEL_ROADMAP.md)；研发愿景不能写成已达到同等模型能力。

平台主链是：

```text
环境检查
  → 数据导入、检查、去重和清单
  → 训练规划与资源估算
  → 预训练 / SFT / 偏好训练 / 蒸馏
  → 独立验证和实际生成评测
  → 基座与候选配对比较
  → 发布门禁
  → 合并、导出和权重审计
  → 推理服务、压测和运行监控
```

所有通用步骤应提供三种稳定入口：

- CLI：适合 SOP、CI 和自动化流水线。
- Python API：适合二次开发和插件。
- YAML/JSON 配置：适合可复现的端到端实验。

## 2. 框架与领域项目的边界

| 能力 | SaddleLLM | 领域项目 |
|---|---|---|
| 模型 | 通用 HF/原生模型加载、adapter、checkpoint、tokenizer | 选择具体基座和许可证确认 |
| 数据 | 通用 schema、格式检查、哈希、去重、切分清单和泄漏检查接口 | 领域数据获取、授权、脱敏、标签定义和专家审核 |
| 训练 | SFT、LoRA/QLoRA、偏好训练、续训、恢复和训练审计 | 领域训练配方与超参数实验 |
| 评测 | PPL、选择题、生成样例、配对统计、报告和发布门禁 | 领域评分器、风险集、专家盲评和业务阈值 |
| 发布 | adapter 合并、格式校验、manifest、哈希和门禁阻断 | 发布审批人、模型卡中的领域限制 |
| 服务 | 标准推理 API、内置低并发对话页、训练仪表盘、鉴权接口、并发限制和健康检查 | 业务权限、领域页面和工作流 |
| 合规 | 通用审计字段、数据来源和实验追踪契约 | 行业法规判断、伦理审查与机构审批 |

禁止把医院名称、护理字段、某个比赛的评分规则或某份数据集的下载脚本写进 SaddleLLM 核心包。它们应通过普通数据文件、配置或插件接入。

## 3. 稳定平台契约

### 3.1 数据契约

- 支持 JSONL/JSON 和明确的字段映射，不依赖某个领域的固定字段名。
- 每个正式数据集保存来源、许可证、版本、记录数、文件哈希和切分策略。
- train、validation、test 必须能执行确定性的重复与污染检查。
- 跨集合检查覆盖 group id、Unicode/标点归一后的精确文本和高相似改写；敏感标识在报告中默认哈希。
- test 是封存集；解封后不得继续用于调参。
- 领域高风险样本的分类和审核状态作为扩展 metadata，不写死在训练器里。

### 3.2 模型契约

- 同一入口加载基座模型、完整 checkpoint 和 PEFT adapter。
- 离线模式必须只使用已经缓存或明确指定的本地文件。
- adapter 保存其基座引用和 PEFT 版本；运行时版本不兼容时提供可执行诊断。
- 导出产物包含配置、tokenizer、权重、来源 checkpoint、评测门禁和可选权重哈希。

### 3.3 训练契约

- 所有训练从同一种顶层 `stages` 配置进入 `TrainingOrchestrator`。
- 配置与数据检查在分配大模型显存前完成。
- 训练汇总保存 global step、train/eval metrics、随机种子、依赖版本和 trainer state。
- completion-only SFT 只对回答 token 计算 loss；无法保证时必须失败，不能静默训练提示词。
- checkpoint 由独立 validation 选择，不能默认认为最后一个 checkpoint 最好。

### 3.4 评测契约

- 基座和候选必须使用同一 tokenizer、模板、数据、截断和解码配置。
- 评测 JSON 保留数据哈希、逐条结果和生成参数；Markdown 提供人可读展示。
- PPL 只说明参考答案 token 的平均不确定性，不代表事实正确率或安全性。
- 客观题同时保留标签概率评测和完整生成评测。
- 客观题可由领域项目提供声明式提示模板；框架报告分模板准确率、最差模板、预测翻转率和所有模板均正确率，不在核心中硬编码领域问法。
- 开放回答可由领域项目提供声明式 rubric；框架生成逐条回答并报告加权分、关键失败和分维度结果，空回答不得靠负向规则通过。
- 发布比较使用同题配对统计，并分别报告 validation 和封存 test。
- validation-only 结果只能选择 checkpoint，必须保持 `accepted=false`；只有配对封存 test 同时达标才允许输出发布晋级。
- 通用框架提供指标和门禁机制；领域专家决定指标含义和发布阈值。

### 3.5 服务契约

- 开发 smoke 服务与生产服务明确分级。
- `max_concurrency` 只是请求保护上限，不等于吞吐能力。
- 生产并发验收必须记录模型、量化、输入/输出长度、并发、成功率、P50/P95/P99、tokens/s 和显存峰值。
- 需要连续批处理时应接入专用推理后端；不得用普通 `model.generate` 宣称百并发生产能力。
- `dashboard` 只读训练标准产物；内置对话页与 API 共用模型实例，不能为了可视化重复加载模型。
- 页面是通用观测与功能验证入口，不替代领域发布门禁、专家审核或生产监控。
- 评估、发布与部署职责分离：评测命令产生质量证据，可选的导出门禁用于自动发布控制，推理命令只加载指定模型并展示已有 release metadata。

### 4.1 接下来要加强的模型能力

这里区分“模型真正会什么”和“框架是否有一个同名模块”。每项都必须有独立测试集、基座
对照和逐条证据：

| 优先级 | 模型能力 | SaddleLLM需要补强的通用能力 | 护理项目如何验收 |
|---|---|---|---|
| P0 | 领域知识与指令能力 | 继续预训练、SFT、蒸馏统一生成基座/候选配对报告，自动发现能力退化 | 护理封存选择题、开放问答和不同提问模板分别比较 |
| P0 | 安全、拒答与不确定性 | 可插拔风险分类、严重错误一票否决、置信度/校准指标、专家审核证据 | 禁忌、剂量、急救顺序、升级上报、越权诊断和未知问题 |
| P0 | 数据稳健性 | 按`source_id/group_id`切分、近重复和跨split污染检查、模板变体评测 | 同一道题的原题、改写题和自然问法不得跨集合 |
| P1 | 检索增强与可追溯回答 | 标准RAG数据/评测契约、引用命中率、证据一致性和无证据拒答 | 回答能引用指定教材/指南版本，证据不支持时不编造 |
| P1 | 工具调用与结构化输出 | function calling训练格式、参数schema校验、工具成功率与恢复评测 | 调用护理知识库、量表计算器、模拟交班系统，不直接执行高风险动作 |
| P1 | 长上下文和多轮一致性 | 长度分桶评测、上下文利用率、关键信息召回、多轮状态与冲突检测 | 长病例、护理记录、医嘱变化和SBAR多轮交班保持一致 |
| P1 | 推理与任务规划 | 过程监督/偏好数据、最终答案与步骤级评分插件，避免只奖励模板长度 | 风险排序、观察—处置—复评—上报闭环，而非只背选项 |
| P2 | 多模态能力 | VLM/语音数据适配、真实训练器、模态联合评测和安全限制 | 压疮图片、设备读数和护理语音仅作辅助，保留人工确认 |
| P2 | 生产推理能力 | 连续批处理后端、吞吐/延迟/显存压测、取消请求和可观测性 | 固定输入输出长度下验证10/50/100并发，不用配置值冒充性能 |

实现顺序应为：评测与数据可靠性 → 安全 → 领域能力 → RAG/工具/长上下文 → 多模态和
生产规模化。否则即使新增很多训练算法，也无法判断它们究竟提升还是损坏了模型。

## 5. 近期开发优先级

### P0：形成可靠的文本大模型发布闭环

1. 把新的 multiple-choice/completion/prompt-robustness evaluator 接入 `TrainingOrchestrator` 的 `eval` stage。
2. 让 eval stage 正确识别“基座 + adapter”和完整模型，不把 adapter 目录误当完整模型。
3. 在同一运行中生成基座、候选、配对比较、门禁和 Markdown 总报告。
4. 建立统一 experiment manifest，串起数据、配置、checkpoint、评测、导出和依赖版本。
5. `export` 默认只能消费通过门禁的评测产物。

### P1：数据与评测插件化

1. 定义 dataset adapter 和 evaluator 插件协议。
2. 提供分类、抽取、生成、RAG、工具调用和安全性评测的标准结果 schema。
3. 允许领域项目注册评分器，但不修改 SaddleLLM 核心训练代码。

### P2：生产推理

1. 将 OpenAI 兼容 API 与模型执行后端解耦。
2. 接入支持连续批处理的 Linux 推理后端。
3. 增加压测命令、Prometheus 指标、队列保护和容量报告。
4. 用可复现压测结果决定 10/50/100 并发机器规格。

## 6. 验收标准

一个领域项目只有在不修改 SaddleLLM 核心源码的情况下，仅通过数据、配置和可选插件就能完成以下流程，才算平台通用性成立：

1. `doctor` 检查环境。
2. `inspect-data` 阻断不合格数据。
3. `validate-config` 和 `plan` 给出训练计划。
4. `train` 产生可恢复 checkpoint 和审计摘要。
5. `evaluate` 评测基座与候选并生成人可读报告。
6. `compare` 给出显著性和晋级结论。
7. `export --require-gate` 只导出通过门禁的模型。
8. `serve` 完成功能验证，生产后端完成独立容量验收。

护理学院项目是当前首个端到端验证项目。其数据授权、护理分类、教师审核和比赛门槛留在项目中；验证出来的通用加载、训练、评测、诊断和报告能力回收到 SaddleLLM。
